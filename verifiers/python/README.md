# VEILOPS independent Python verifier

This is a second implementation of the `veilops-range-v1` and `veilops-range-v2` verifiers, written separately from the
TypeScript reference (`packages/proof-engine`). It is written from the specifications: RFC 9496
(ristretto255), RFC 9380 (hash-to-curve), RFC 8032 (Ed25519) and the `encoding` sections of
`test-vectors/veilops-range-v1.json` and `test-vectors/veilops-range-v2.json`. It was not produced by transliterating the TypeScript
library internals. Its only job is to cross-check the reference test vectors. If two separately
written implementations agree on every vector, an encoding or arithmetic bug in either one is
much less likely to go unnoticed.

**This is not an external audit.** Both implementations come from the same project, and passing
these checks says nothing about whether the protocol design is sound.

## Requirements

Python 3.10 or newer, standard library only (no pip packages). It has also been run on 3.9 and 3.13.

## Run

From the repository root (`veilops/`):

```sh
# default (CI): both proof systems
python3 verifiers/python/veilops_verify.py test-vectors/veilops-range-v1.json test-vectors/veilops-range-v2.json
# failures + one summary line only
python3 verifiers/python/veilops_verify.py test-vectors/veilops-range-v1.json test-vectors/veilops-range-v2.json --quiet
```

You can pass one or more vector files. Each file's proof system is detected from its `name`
field (`veilops-range-v1 ...` or `veilops-range-v2 ...`). A file with an unrecognised name counts
as a failure. The RFC self-tests run once per invocation. The summary line gives the total and a
count for each file.

The exit code is 0 only if all RFC self-tests pass **and** every case in every file matches its
`expected` verdict. Otherwise it is 1, or 2 for a usage error. A run over both files takes about
8 seconds: around 3 s for v1 and 5 s for v2.

## What it checks

RFC self-tests. These validate the curve code on its own, with no VEILOPS data involved. The
values are in `rfc_vectors.py`.

| Source | What |
|---|---|
| RFC 9496 §4.1 | implementation constants (derived in code, then compared with the RFC) |
| RFC 9496 App. A.1 | encodings of B[0..15]: encode, decode, re-encode, addition, scalar multiplication |
| RFC 9496 App. A.2 | all 29 invalid encodings are rejected (non-canonical, negative, non-square, negative xy, s = -1) |
| RFC 9496 App. A.3 | element derivation / one-way map (§4.3.4): 7 pairs plus the 4 inputs that share one output |
| RFC 9496 App. A.4 | `SQRT_RATIO_M1` |
| RFC 9380 App. K.3 | `expand_message_xmd(SHA-512)`: 10 vectors |
| RFC 8032 §7.1 | Ed25519 TEST 1-3: public key from seed, deterministic signature, verify, and 3 tampered variants rejected (message changed, S + L, R changed) |
| extra | Ed25519 decoding rejects y >= p; malformed v1 range-proof, policy and record inputs, and malformed v2 proof bytes and public inputs, return False without raising |

`rfc_vectors.py` was generated by parsing the RFC plain-text files fetched from
rfc-editor.org. Its header records the SHA-256 of each file.

v1 vector file checks (`test-vectors/veilops-range-v1.json`):

- `encoding.L` is the group order. `generators.G` is the ristretto255 base point.
  `generators.H` is recomputed as `hash_to_ristretto255(msg, DST)` (RFC 9380 expand_message_xmd
  with SHA-512 and 64 output bytes, then the RFC 9496 one-way map).
- `attestation.publicKey` is derived from `attestation.seedHex` (RFC 8032 key generation).
- `commitments`: C = v·G + r·H.
- `challenges`: SHA-512(utf8(domain) || per part u32be(len) || part), read little-endian, mod L.
- `rangeProofs`: CDS OR-proof per bit, using challenge share sums and Σ 2^i·C_i = C. Points must be
  canonical ristretto255 encodings. Scalars must be 64 lowercase hex characters and < L. The
  bit count n must equal the number of bit proofs and lie in 1..64.
- `policyProofs`: the system label, 1 <= rangeBits <= 48, both proofs with n = rangeBits,
  maxAmount a safe integer in [0, 2^n), the lower proof on C with `ctx|lower`, and the upper proof
  on D = maxAmount·G − C with `ctx|upper`. Each case is also checked for `transcriptContext` =
  canonical JSON of `{v, ...publicInputs}` and `proofId` = `prf_` + first 20 hex characters of
  SHA-256(canonicalJson(proof)).
- `records`: base64 → JSON proof, policy verification against the record's public inputs, the
  proofId binding, and an Ed25519 attestation over
  `utf8("VEILOPS/record/v1|" + canonicalJson(record without attestation))`. `valid`,
  `attestation` and `proofIdMatches` are compared with `expected`.

v2 vector file checks (`test-vectors/veilops-range-v2.json`). The statement and generators are
the same as v1. The encoding is binary and Fiat–Shamir uses SHA-256, so the proof can be verified
on-chain.

- `contexts`: recomputes the transcript context, canonical JSON of
  `{v: "veilops-range-v2", ...publicInputs}`. Recomputes
  `ctxHash = SHA-256("VEILOPS/range/v2|" || ctx || "|lower" / "|upper")`, and the bit challenge
  `e = LE(SHA-256(0x00||T) || SHA-256(0x01||T)) mod L` with
  `T = "VEILOPS/range/v2/bit" || ctxHash || u32be(i) || C_i || A_0 || A_1`. The challenge is
  compared as a 32-byte little-endian value with `expectedLE`. The vector's challenge is built
  over `ctxHashLower`.
- `cases`: strict decoding of `proofHex`, laid out as
  `u8 version (=2) || u8 n || n lower bits || n upper bits`, with
  `bit = C_i(32) || c0 || c1 || s0 || s1` and 32-byte little-endian scalars. The decoder requires:
  - total length exactly 2 + 2n·160 and 1 <= n <= 48
  - every scalar < L and every C_i a canonical ristretto255 encoding
  - n == rangeBits
  - text fields matching `[A-Za-z0-9_.-]{1,64}` (full match; non-strings rejected)
  - maxAmount a safe integer in [0, 2^rangeBits)
  - amountCommitment 64 lowercase hex characters and a valid point

  Then it verifies each CDS bit proof, Σ 2^i·C_i = C (lower) and Σ 2^i·C_i = maxAmount·G − C
  (upper), and `proofId = "prf_" + SHA-256(proof bytes)[:20 hex]`. Each case's verdict and
  failure reason are printed.

## Notes and known differences from the TypeScript reference

- Arithmetic is variable time, which is fine because verification only touches public data.
  `ed25519_sign` exists only for the RFC self-test. Do not use it with real keys.
- Ed25519 verification is strict. It rejects S >= L and y >= p, and it uses the cofactored
  equation from RFC 8032 §5.1.7. `@noble/curves` defaults to ZIP-215 rules, which accept some
  non-canonical encodings. The two can disagree on adversarial signatures, but none appear in
  the vectors.
- Point and scalar hex must be lowercase, as the vector `encoding` section specifies. The
  TypeScript side accepts uppercase point hex through noble's `hexToBytes`.
- Canonical JSON sorts keys by UTF-16 code units, as JS `sort()` does, and prints integral
  numbers as integers. Non-integral floats use Python's shortest repr, which matches JS for
  ordinary magnitudes. The protocol only puts integers and strings into hashed or signed JSON.
- v2 text fields must be actual strings here. The TS `validatePublicInputsV2` uses
  `RegExp.test`, which coerces its argument, so a number such as `123` would pass. The Rust
  program takes `String` arguments. No vector exercises this.
